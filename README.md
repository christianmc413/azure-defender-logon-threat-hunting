# Microsoft Defender Logon Threat Hunting with KQL

> Portfolio project demonstrating threat hunting in Microsoft Defender using the `DeviceLogonEvents` table and Kusto Query Language (KQL) to investigate suspicious authentication activity.

## Overview

This project documents two threat-hunting use cases performed against endpoint logon telemetry in Microsoft Defender. The goal was to use KQL to identify authentication patterns that can indicate password-guessing activity or a possible account compromise, and then apply analyst context before deciding whether the activity is malicious.

The investigations focus on:

1. **Failed logons / brute-force indicators**
2. **Successful logons following repeated failures**

A major lesson from this lab was that a KQL result is a **lead, not a verdict**. High failed-logon counts can be generated by legitimate security tooling as well as attackers, so context and enrichment matter before escalating an event.

`DeviceLogonEvents` provides authentication-related telemetry that can be filtered and summarized to identify suspicious logon patterns.

# Investigation 1: Failed Logons / Brute-Force Detection

## Objective

Identify devices and remote IP addresses producing a high number of failed authentication attempts. Repeated failures from the same source can be an indicator of password guessing or brute-force activity and should be reviewed in context.

## KQL Query

```kusto
let startTime = datetime(2026-06-01 00:00:00);
let endTime   = datetime(2026-06-02 00:00:00);

DeviceLogonEvents
| where TimeGenerated between (startTime .. endTime)
| where ActionType == "LogonFailed"
| summarize FailedCount = count(),
            Accounts = make_set(AccountName, 20)
    by RemoteIP, DeviceName, FailureReason
| where FailedCount > 10
| sort by FailedCount desc
```

## What the Query Is Looking For

The query:

1. Searches `DeviceLogonEvents` during the defined investigation window.
2. Keeps only events where `ActionType == "LogonFailed"`.
3. Groups failed attempts by `RemoteIP`, `DeviceName`, and `FailureReason`.
4. Counts the failed attempts and collects up to 20 associated account names.
5. Removes results with 10 or fewer failed attempts.
6. Places the highest failed-logon counts at the top.

### Threat this hunt can help surface

**Brute-force / password-guessing activity.** A source generating repeated authentication failures can warrant investigation, especially when the volume, targeted accounts, device, IP reputation, or surrounding activity does not match expected behavior.

### My Analysis

One result involving **`earnest-linux-machine`** initially looked suspicious because it appeared in the brute-force hunt with repeated failed authentication activity.

After adding environmental context, however, I determined that the activity was associated with the environment's **Tenable scanner performing a routine scan of the VNet** rather than an actual threat actor.

### Analyst Takeaway

This was an important example of why **context is critical during log analysis**. A detection query can identify behavior that resembles an attack, but similar telemetry can also be produced by authorized scanners, vulnerability-management tools, automation, or administrators.

If I treated every high failed-logon count as malicious without validating the source, I could create unnecessary alerts and false-positive investigations.

**Key lesson:** Detection finds the signal. Investigation determines what the signal means.

# Investigation 2: Successful Logon Following Repeated Failures

## Objective

Look for the more concerning sequence where the same account, device, and remote IP generate repeated authentication failures **and also record successful authentication** during the investigation window.

A successful authentication associated with a source that also generated many failures can warrant additional investigation because the pattern may be consistent with repeated password attempts eventually reaching a valid credential.

## KQL Query

```kusto
let startTime = datetime(2026-06-01 00:00:00);
let endTime   = datetime(2026-06-02 00:00:00);

let failures =
    DeviceLogonEvents
    | where TimeGenerated between (startTime .. endTime)
    | where ActionType == "LogonFailed"
    | summarize Failures = count()
        by AccountName, DeviceName, RemoteIP;

let successes =
    DeviceLogonEvents
    | where TimeGenerated between (startTime .. endTime)
    | where ActionType == "LogonSuccess"
    | summarize Successes = count(),
                LastSuccess = max(TimeGenerated)
        by AccountName, DeviceName, RemoteIP;

failures
| join kind=inner successes on AccountName, DeviceName, RemoteIP
| where Failures > 10 and Successes > 0
| project AccountName,
          DeviceName,
          RemoteIP,
          Failures,
          Successes,
          LastSuccess
| sort by Failures desc
```

## What the Query Is Looking For

This query creates two datasets:

### `failures`
Counts failed logons by:

- Account
- Device
- Remote IP

### `successes`
Counts successful logons using the same account/device/IP combination and records the latest success time.

The query then performs an inner join so that only combinations appearing in **both** sets survive. Finally, it keeps results where:

- `Failures > 10`
- `Successes > 0`

### Threat this hunt can help surface

**Possible credential compromise following repeated password attempts.** The combination of many failed attempts and one or more successful authentications makes the activity more important to investigate than failures alone.

### My Analysis

During this hunt, I identified a result with **more than 200 failed logon attempts and 15 successful logons** associated with the same account/device/remote-IP grouping. In the lab investigation, the remote IP was also **flagged as suspicious**.

Compared with a simple failed-logon spike, the presence of successful authentication makes the activity a higher-priority lead because it indicates that the source was not only generating failures but was also associated with successful access.

### Analyst Response

I would create or escalate an alert for investigation and validate whether the successful authentications were authorized.

If additional evidence confirmed that the source was malicious and unauthorized access had occurred, I would escalate the incident to the incident-response team so containment and remediation actions could be considered under the organization's incident-response procedures.

### Analyst Takeaway

This investigation shows why authentication hunting should not stop at failed logons. A failure-only query is useful for finding password-guessing behavior, while correlating failures with successes can surface events that deserve greater urgency.

# Comparing the Two Hunts

| Hunt | Signal | Why it matters |
|---|---|---|
| Failed-logon brute-force hunt | More than 10 failed attempts grouped by remote IP, device, and failure reason | Helps identify sources producing repeated authentication failures |
| Failure + success correlation | More than 10 failures plus at least one success for the same account, device, and remote IP | Helps prioritize cases where repeated failures coexist with successful authentication |

The first hunt taught me the importance of **false-positive validation**. The second taught me how combining related log patterns can create a stronger investigative signal.

# Investigation Workflow I Practiced

```text
KQL detection
    |
    v
Review suspicious result
    |
    v
Add context and enrichment
    |
    +--> Known authorized activity? --> Document / tune / close as appropriate
    |
    `--> Still suspicious? --> Investigate related activity
                                  |
                                  v
                             Alert / escalate
                                  |
                                  v
                         Incident response if confirmed
```

For me, the main point of the lab was that the query is only the beginning of the investigation. The analyst still has to determine what the activity represents in the context of the environment.

# Key Takeaways

- Repeated failed logons can be an indicator of brute-force activity, but they can also come from authorized tooling.
- Asset and scanner context helped distinguish the `earnest-linux-machine` activity from a more suspicious result.
- IP enrichment increased the priority of the second failed-logon finding during the lab investigation.
- Correlating failed and successful authentication events produced a stronger lead than examining failures alone.
- A detection result should be investigated before it is labeled a confirmed attack.
- Good SOC analysis combines **query logic + context + enrichment + escalation judgment**.
